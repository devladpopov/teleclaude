# Правила оформления ответов в Telegram

Шаблон правил, которые получает каждый spawn. Бот показывает файл по
`/rules`, краткая выжимка зашита в system prompt роутера. Правь под
себя: изменения подхватятся при следующем сообщении.

## Стиль

- Пиши нормальной прозой. Абзацы по 2-4 предложения, между абзацами
  пустая строка. Внутри абзаца строки не режь: Telegram сам переносит
  текст, ручные переносы дают «лесенку».
- Длинное и среднее тире как пунктуацию не используй, это маркер
  LLM-стиля. Замени запятой, двоеточием или точкой. Дефис в словах
  (`bat-wrapper`, `topic-memory.md`) нормален.
- Эмодзи не использовать, если пользователь явно не попросил.
- Без вступлений и постамбулы («я сделал то и сё», «хочешь ещё?»).
  Если нужен выбор, задай один конкретный вопрос.
- Не вставляй сырой вывод команд. Перескажи, важное дай коротким
  блоком кода или списком.
- Сообщение длиннее ~4000 символов разбивай на два.

## Пути к файлам

Всегда абсолютные: пользователь не помнит твой cwd и может читать
с другой машины.

ПЛОХО: «смотри в `src/router.ts`»

ХОРОШО: «смотри в `C:\path\to\teleclaude\src\router.ts`»

Правило действует везде: в ответах, в `LAST_ACTION` в CHECKPOINT.md,
в сообщениях коммитов.

## Таблицы

Telegram не рендерит markdown-таблицы (`| a | b |`) в обычном
сообщении. Таблицу оборачивай в блок из трёх обратных кавычек:

```
Колонка1   Колонка2
value1     value2
foo        bar
```

- Колонки выравнивай пробелами, заголовок без строки `---`.
- Не больше ~38 символов в строке: на телефоне длинная monospace-строка
  заворачивается и таблица разваливается.
- Один ряд = одна строка, без «хвостов» на следующей строке.
- Длинные значения с пояснениями это не таблица, а обычный список.

## Тексты для копирования

Если кладёшь в блок кода готовый текст (письмо, пост, черновик
сообщения), пиши его как обычную прозу: абзац одной длинной строкой,
абзацы через пустую строку. Ручные переносы запекаются в текст и
ломают его при пересылке. Переносы по ширине нужны только таблицам и
коду.

## Код и ссылки

- Однострочный код в одинарных обратных кавычках, многострочный в
  блоке. Язык после ``` не указывай: Telegram покажет его первой
  строкой.
- Ссылки можно писать голым URL, Telegram сделает их кликабельными.

## Префикс модели

Каждое сообщение начинается с `[<tag>]` модели, например `[opus-4.7]`.
Роутер подставляет тег сам, если модель его забыла, но не убирай его.

## Молчание между tool calls и обязательный финал

Роутер отправляет каждый текстовый блок между tool calls отдельным
сообщением. Не комментируй каждый шаг: делай вызовы подряд и пиши один
итоговый ответ. Для длинной задачи допустим один промежуточный апдейт.

Финальный ответ обязателен всегда, хотя бы одна строка «готово: <что
именно>». Пустой ответ пользователь видит как ошибку. В финале: что
сделано, хеш и ветка коммита, URL деплоя, какие файлы и где.

## Делегирование в другой топик

Сообщение бота в чужой топик там ничего не запускает: роутер реагирует
только на сообщения пользователей из `allowedUsers`. Чтобы другой топик
выполнил работу, используй MCP-инструмент `trigger_topic` из
`mcp-router`:

```
trigger_topic({ topicKey: "-1001234567890:42", text: "Проверь CHECKPOINT.md и обнови статус." })
```

Свой topicKey даёт `current_topic()`. Каждый trigger это отдельный
spawn (токены, квота), не злоупотребляй.

## Запланированные задачи

Источников ровно два, других имён не выдумывай:

- `config/reminders.json`: `/remind` (текстовое напоминание) и
  `/remind --do` (в указанное время запускается spawn с текстом).
- `config/recurring.json`: `/loop <интервал> <текст>`, повторяющиеся
  spawn'ы.

На вопрос «что запланировано» прочитай оба файла и покажи короткую
таблицу. Сам эти файлы не редактируй, это live-state планировщика.
Для изменений есть `/unloop <id>` и `/unremind <id>`.

## Большие задачи по частям

Если нужно изменить или сгенерировать больше ~300 строк, не делай это
одним шагом: spawn упадёт по idle timeout. Работай чанками по 100-300
строк, после каждого сохраняй файл и обновляй CHECKPOINT.md
(`LAST_ACTION: строки 301-600 из 1891`, `NEXT: 601-900`). Если работа
не поместилась в один spawn, Director увидит прогресс и запустит
следующий.

## После compaction

Строка «Continue from where you left off» не означает «повтори
работу». Сначала прочитай CHECKPOINT.md. Если `STATUS: COMPLETED`,
ответь, что всё готово, и остановись. Перед деплоем или миграцией
проверь текущее состояние. Не повторяй успешный tool call без новой
причины.

## Браузер

Страницы и локальные файлы открывай только через playwright-MCP
(`browser_navigate`), в браузере, который видит пользователь. Не
используй `start`, `explorer` или `cmd /c start`: они открывают другой
профиль, и пользователь не увидит вкладку. Для локального HTML годится
`file:///` URL или `python -m http.server`; `npx serve` не подходит,
он отдаёт `index.html` на любой путь.

## Проверяй то, что публикуешь

Exit code 0, успешный push или собранный билд не означают «готово».
Прежде чем отчитаться о сайте, открой URL и проверь HTTP-статус и
консоль. Об API: дёрни его и посмотри код и тело ответа. О файле:
открой и проверь содержимое. В отчёте напиши, что именно проверил.
Если проверить не можешь, так и скажи: честное «не проверено» лучше
ложного «готово».
